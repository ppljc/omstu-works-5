ется в трех версиях:

осуществляется к экземпляру MongoDB (Isolated Edition).

ТЕОРЕТИЧЕСКИЕ СВЕДЕНИЯ 
Основными строительными блоками для хранения и управления да н-
ными в MongoDB являются базы данных, коллекции и документы. Доку-
менты организованы в коллекции, которые хранятся в базах данных. 
База данных в MongoDB – это контейнер для данных, который содер-
жит ряд коллекций. MongoDB позволяет создавать несколько БД на одном 
сервере, причем каждая из них логически изолирована от других. Это с а-
мый высокий уровень структуры в данной системе. 
При запуске MongoDB создаются три БД по умолчанию: admin, config 
и local, которые используются для внутренних целей. 
Ограничения на именование баз данных: 
• имена не должны учитывать регистр; 
• имена не могут содержать специальные символы (/, . , $, *, | и т. д.); 
• имена не могут содержать символы null (в системах Windows, Unix 
и Linux); 
• имена не могут быть пустыми и должны содержать  не более  
64 символов. 
Коллекция в MongoDB похожа на таблицу в реляционных БД. Она 
представляет собой контейнер, содержащий группу документов, и являет-
ся частью БД. Коллекции обеспечивают структуру данных, но они не 
имеют схемы (БД MongoDB тоже не имеют схемы). Поэтому схема одного 
документа в коллекции не обязательно должна быть похожей на схему 
другого. Одна коллекция может содержать разные типы документов, и од-
=== PAGE 15 ===
16 
на БД может содержать несколько коллекций, каждая из которых хранит 
разные типы документов. 
Коллекции могут иметь семантическое значение, но в целом они 
представляют собой просто способ разделения различных наборов док у-
ментов в системе. Можно назначать разные свойства разным коллекциям  
и выполнять действия с конкретными коллекциями документов. 
Ограничения на именование коллекций: 
• имя должно начинаться с символа подчеркивания ( _) или буквы  
(a–z или A–Z); 
• имя не должно начинаться с цифры, префикса system. (зарезервиро-
ван для системных коллекций MongoDB), содержать символ $, пустую 
строку, символ null; 
• максимальная длина имени составляет 120 байт (включая имя БД, 
точку-разделитель и имя коллекции). 
Документ – это контейнер для информации, представляющей одну за-
пись или объект, содержащий связанные описательные данные. Докуме н-
ты могут иметь гибкую структуру, не обязательно совпадающую со струк-
турой других документов той же коллекции, а также быть вложенными.  
Документы MongoDB используют фор мат сериализации данных 
BSON (двоичное представление нотации JSON JavaScript). Это обеспеч и-
вает организованную структуру с определенными типами данных, которые 
можно запрашивать и обрабатывать программно. 
Документы BSON представлены парой фигурных скобок { }, которые 
содержат пары «ключ-значение» и «поле-значение». Поле идет первым  
и отображается в виде строки . Значение может иметь любой допустимый 
тип данных BSON. Между полем и его значением стоит двоеточие. Запя-
тые отделяют пары полей и значений друг от друга: 
{ _id: 80380, 
vehicle.type: "car",

Типы данных в MongoDB 
Пользователь MongoDB способен гибко выбирать структуру данных. 
Он не привязан к определенной схеме и для любого поля документа может 
использовать любой доступный тип данных MongoDB. При этом следует 
применить и схему, чтобы добавить проверку коллекций. Если схема есть, 
то она может повлиять на типизацию данных. При планировании БД важ-
но понимать, как выбрать нужный тип данных. Это будет определять рабо-
ту с данными и способ их хранения. 
Рассмотрим типы данных, используемых в MongoDB. 
1. JSON и BSON. 
MongoDB и другие документные БД NoSQL применяют формат JSON 
(нотацию объектов JavaScript) для представления записей данных в виде 
документов. Преимущества использования JSON: 
• простота чтения, изучения и узнаваемость конструкций; 
• гибкость формата, будь то разреженный, иерархический или глубо-
ко вложенный; 
• самоописание, облегчающее приложениям работу с данными; 
• возможность применять минимальное количество основных типов. 
Документы в MongoDB рассматривают как JSON-подобные в том

MongoDB понимает структуру вложенных документов и может и с-
пользовать их для создания индексов, выполнения запросов и обновлений. 
Вложенные документы могут изменить способ работы с данными.  
В реляционных СУБД документ моделируется как две строки в двух ра з-
ных таб лицах ( person и addresses). В MongoDB можно встраивать док у-
мент address в документ person. 
Однако в случае с MongoDB избыточность данных может быть выше. 
Допустим, что addresses были отдельной таблицей в реляционной БД,  
и нужно было исправить опечатку в адресе. При соединении таблиц person 
и addresses получали обновленный адрес для всех, кто использует его. При 
работе с MongoDB нужно исправлять опечатку в документе каждого чел о-
века.

В MongoDB нет явной команды для создания новой базы данных. Но это

ТЕОРЕТИЧЕСКИЕ СВЕДЕНИЯ 
При создании документной базы данных  не требуется предварител ь-
ное проектирование схемы, но в соответствии с правилами ER-моделиро-
вания выделить можно сущности, атрибуты и связи. Если есть схема рел я-
ционной базы данных, следует ориентироваться на нее. Необходимо опре-
делить состав коллекций и логические связи между ними. 
В MongoDB, в отличие от реляционных СУБД, нет встроенных мех а-
низмов для JOIN-операций между коллекциями, но есть несколько спосо-
бов организации связей между документами разных коллекций.  Это сле-
дующие способы: 
1. Встраивание документов (Embedding). 
2. Ссылки по идентификатору ObjectId (Referencing). 
3. Гибридный подход. 
В лабораторной работе № 3 мы применяли встраивание документов. 
Встроенные структуры являются гибкими и позволяют хранить больше 
информации в одном документе. 
Преимущества встраивания: 
• не нужно делать два запроса к разным коллекциям; 
• есть возможность использования атомарных операций обновления; 
• есть возможность создания сложных структур с несколькими уров-
нями вложенности. 
Недостатком встраивания является то, что максимальный размер доку-
мента в MongoDB составляет 16 М б, поэтому подход нельзя использовать
